# Manual PIM Numbering (supersedes Batch 5H-b auto-allocation)

Status: **code-complete**, 2026-10-07, production-completion sprint.

## What changed and why

Batch 5H-b (`docs/phase6-batch5h-b-pim-numbering.md`) auto-allocated the next
PIM number from `pim_number_sequences` (one row per year, atomic
`UPDATE ... SET last_number = last_number + 1 ... RETURNING`). Mid-sprint,
the production policy changed: **the PIM number is the official number from
the physical PIM/Assignment Register**, and must be entered by staff, not
generated by software. Auto-allocation risked staff and software numbers
silently drifting apart.

## New workflow

```
SCRUTINY COMPLETE
  -> PIM_NUMBER_PENDING
  -> staff enters the official running number (+ year) from the register
  -> system validates (hard blocks / warnings, below)
  -> staff confirms if warned
  -> PIM number stored
  -> FORM2_PENDING
```

Staff types only the running number (e.g. `119`); `PIM/119/2026` is derived
(`formatPimNumber`), matching the existing format.

## Schema (additive, migration `20261007000000_manual_pim_numbering.sql`)

- `pim_cases.running_number integer`, `pim_cases.pim_year integer` — new,
  nullable columns. Backfilled from any existing `pim_number` string on a
  best-effort basis (verified against the live `pim-system` Supabase
  project before migrating: `pim_number` was `NULL` on every row, so the
  backfill was a no-op in production).
- `unique index uq_pim_cases_year_running_number on pim_cases (pim_year,
  running_number) where running_number is not null` — the hard duplicate
  block, enforced by the database itself, not just application code.
- `pim_number_corrections` table — append-only audit trail for the
  controlled-correction action (below).
- `pim_number_sequences` is **kept, not dropped**, for historical/rollback
  reference. Verified live before this change: `year=2026,
  last_number=118` — untouched, and no longer read or incremented by the
  normal staff route.

## Validation rules (`lib/pim-data/pim-numbering.js`: `assignPimNumberManualTx`)

| Input | Result |
|---|---|
| Zero / negative / non-numeric running number | **Hard block** (thrown error, nothing written) |
| Duplicate `(year, running_number)` | **Hard block** — checked explicitly for a clear message, and backstopped by the unique index under concurrency (two staff submitting the same number at once: one wins, the loser's `INSERT`/`UPDATE` hits the unique-violation and is converted to the same clear error) |
| Running number `> last registered + 1` (a gap) | **Warning only**, e.g. "Previous registered number is 118. PIM/119/2026 is not recorded. Please verify the official register." Nothing is written until the caller re-submits with `confirmGap: true` |
| Running number `<= last registered` (lower/out-of-sequence, not already used) | **Warning only**, same confirm-then-proceed pattern (`confirmLower: true`) |
| Case not in `PIM_NUMBER_PENDING`, or already has a `pim_number` | Hard block (existing business guard, unchanged) |

No warning is a soft client-side-only check: the route itself
(`POST /api/pim/pim-number`) re-validates everything server-side inside the
same locked transaction, so a client that skips the confirmation UI still
cannot bypass the gate.

## Correction (controlled, audited)

Once registered, a normal staff user cannot edit `pim_number`/
`running_number` through the assignment route (it only ever fires when no
number exists yet). The only way to change it is
`POST /api/pim/pim-number/correct/[id]` -> `correctPimNumberPg`, which:

- requires a non-empty `reason`,
- re-checks the duplicate constraint (excluding the case being corrected),
- writes the new number,
- inserts one row into `pim_number_corrections` (old number, new number,
  old/new running number, year, reason, `corrected_by`, `corrected_at`).

## Number reuse

The registration number is permanent history. Nothing in this module (or
the Non-Starter/outcome code elsewhere in the codebase) frees, recycles, or
re-validates a running number when a case later becomes Non-Starter,
settled, failed, withdrawn, or closed — the unique index has no exception
for terminal states, so a closed case's number can never be reissued.

## Tests

`scripts/test-pim-manual-numbering-postgres.js` exercises this against a
dedicated test year (never the real current year/118/119) and covers:
duplicate rejection, gap warning + confirmed continuation, lower-number
warning, invalid-number rejection, concurrent same-number race (one wins,
one fails), and correction audit insertion. Per the sprint's test
discipline, run in isolation, never concurrently with another PostgreSQL
fixture suite.

## What is intentionally unchanged

`assignPimNumberTx` / `assignPimNumberPg` (the Batch 5H-b auto-allocator)
are left in `lib/pim-data/pim-numbering.js` verbatim, for historical/
rollback reference only. Nothing in the normal staff route calls them.
`previewNextPimNumber` likewise remains, unused by the UI, for the same
reason.
